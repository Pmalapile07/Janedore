- **iOS layout and safe areas:** test notch/Dynamic Island and home-indicator safe areas, status/navigation bars, keyboard appearance, scrolling, fixed bottom actions and orientation/viewport resizing. No content should hide behind system UI or the keyboard.
- **Native-feeling interaction details:** check keyboard focus and dismissal, form validation and error placement, pull/scroll behaviour, swipe conflicts, disabled/loading button states, pressed states, haptics only where useful and supported, and preservation of state when navigating back.
- **Visual consistency:** establish consistent spacing, typography, icon sizing, borders, corner radii, colours and component states. Keep JANEDORE's existing fashion-house visual identity; use Apple HIG as interaction guidance, not as a reason to make the brand look like a generic Apple app.
- **Capacitor reliability:** verify status-bar and navigation-bar appearance, app icon/splash screen, launch behaviour, offline/network failure messaging, external links, deep links/Universal Links and Android App Links where applicable. Check that web-only browser assumptions do not break inside the native WebView.
- **Performance:** inspect slow screens, image loading and resizing, unnecessary repeated requests/renders, long lists, memory use and WebView responsiveness. Optimise large product imagery and avoid blocking the main UI thread.
- **Accessibility:** test VoiceOver and Android screen readers, accessible labels, logical focus order, text scaling/contrast, reduced motion and meaningful announcements for loading/errors/success.
- **Device testing and launch gate:** test on a real iPhone and Android device as well as small/large simulators or emulators. Exercise first launch, returning launch, slow/failed internet, login, search, product browsing, variants, cart, checkout/payment return, order tracking, account flows, back navigation and interrupted/resumed sessions. Fix visible jank, flicker, dead taps, layout shifts, keyboard/safe-area bugs and broken navigation before release. Record the devices and test results; do not call the app launch-ready based only on desktop browser testing.

## Vendor product CSV imports and approvals
- **Bulk product upload:** add a CSV import option to the vendor dashboard so a vendor can upload a product catalogue instead of creating products one by one. Support the standard Shopify product CSV format as the primary starting format, since brands may already export their products from Shopify. Provide a downloadable JANEDORE template too, with clear column instructions.
- **Admin-assisted imports:** Admin and Super Admin must also be able to upload a CSV on behalf of a selected vendor/brand. Enforce permissions server-side: vendors can only submit imports for their own brand; Admin can submit for brands they are authorised to manage; Super Admin can manage all brands.
- **Import mapping and preview:** detect Shopify CSV headers and map supported fields to JANEDORE product fields. Before submission, show a preview with product count, variants/options, prices, stock, SKUs, descriptions, product images and any unmapped columns. Allow field mapping where practical and explain which fields will not be imported. Do not silently discard data.
- **Validation and error report:** validate required fields, prices, variant combinations, stock values, image URLs and product/brand associations. Detect duplicate products/SKUs and malformed rows. Show row-level errors and allow the uploader to correct the CSV and re-upload; do not partially publish a failed import.
- **Images and variants:** support Shopify image URL columns and multiple product images where possible; handle colour/size options and variant-level price, SKU and inventory correctly. Clearly report inaccessible image URLs and unsupported Shopify data (for example, custom metafields) rather than pretending they imported.
- **Approval is mandatory:** every vendor or Admin CSV submission enters a Super Admin review queue. Imported products remain unpublished/draft and cannot appear on the public shop, be added to carts or be purchased until a Super Admin approves the import. Super Admin reviews the preview, validation results and affected products, then approves or rejects with an optional reason. Record who submitted, who reviewed, timestamps and the decision. Do not allow an uploader to approve their own submission unless they hold the Super Admin role and explicitly complete the approval action.
- **Safe import behaviour:** stage and validate the complete import before writing products. Use server-side checks and trusted vendor ownership; never trust vendor IDs, prices, stock or approval status supplied by the browser. Prevent duplicate submissions and repeated imports from creating duplicate products. Define how existing products are matched and updated (SKU/Shopify handle or an explicit update mode); default to creating drafts rather than overwriting live products. Preserve existing product records and images unless an authorised update is explicitly approved.
- **Import history:** provide an import history with status (Draft, Submitted, Needs changes, Approved, Rejected, Failed), product counts, errors, submitter/reviewer and timestamps. Allow the submitter to see feedback and resubmit corrected files.

## Admin request centre
- **One Requests section:** add a central Requests area in Admin so requests are not scattered across different screens or lost in messages. It should accept different request types, not only product imports. Start with a flexible request record containing a category/type, title, description, requester, related vendor/brand or order where relevant, attachments, status, assigned staff member, priority, comments/replies and timestamps.
- **Initial request types:** include product CSV imports, product changes, brand/vendor changes, promotions or campaign requests, operational/shipping requests, account/access requests and Other. Keep the type list easy to extend; do not build a separate workflow for every type at launch.
- **Role-based access:** vendors can create and view requests belonging to their own account/brand and reply to requests; Admin can review and manage requests within their permissions; Super Admin can see and manage all requests and make decisions requiring Super Admin approval. Enforce access in trusted backend/database rules, not only by hiding UI.
- **Request workflow:** support New, In review, Waiting for vendor, Needs changes, Approved, Rejected and Completed statuses. Allow staff to assign requests, add internal notes that vendors cannot see, send vendor-visible replies, request more information and record approval/rejection reasons. Keep a complete activity/audit history.
- **Approval boundaries:** requests that change published products, vendor permissions, payouts, policies or other sensitive platform data must use the relevant existing Super Admin approval controls. A request being marked Completed must not itself bypass those controls.
- **Vendor experience and notifications:** show vendors a simple Requests page with their submissions, current status, latest response and a way to reply or attach requested information. Notify the relevant vendor/staff when a request is submitted, assigned, updated or awaiting their response, using the existing email/notification system where appropriate.
- **Admin overview:** show request counts by status and make it easy to filter/search by type, vendor, status, assignee and date. Keep the first version practical and consistent with the existing Admin UI; avoid turning it into an overcomplicated ticketing system.
