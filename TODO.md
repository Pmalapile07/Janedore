## Bob Go integration
- **Tracking updates (built, off):** `bobgo-api.js` takes Bob Go's tracking/updated webhook and marks orders Shipped and Delivered by itself. To switch on: set `BOBGO_WEBHOOK_SECRET` (Bob Go: Settings → Webhook subscriptions → generate a secret) and subscribe `https://janedore.co.za/api/bobgo/webhook` to `tracking/updated`. Orders are matched by the tracking number on each package, so the number in admin must be Bob Go's tracking reference.
- **Checkout options:** customers pay delivery. Show the cheapest Bob Go option, plus a faster one only if it arrives sooner; per brand parcel, added together.
- **Shipping methods:** replace the single "Standard" R150 option at checkout with Bob Go's shipping methods and rates (`checkout.html` shipping card, `cart.js` `getCartShipments()`, `server.js` `priceOrder()`).

- **Shared warehouses:** check that brands sharing a warehouse (Admin > Brands > Warehouse) are booked as one Bob Go shipment.

## Money: delivery fees and Bob Go
- **Who pays what:** the customer's delivery fee comes in through PayFast with the order; Janedore pays Bob Go from a prepaid Bob Go balance. Talk to Bob Go (billing +27 12 940 1060) and PayFast about the details.
- **Cash flow:** PayFast pays out a few days after an order, but Bob Go needs the money in the balance before a courier is booked. Decide how big a float to keep.
- **Courier adjustments:** Bob Go's price is an estimate; if the courier measures a parcel bigger or heavier, the difference is charged afterwards. Decide who covers it (ask brands for accurate weights and sizes).
- **Free delivery:** each brand's own offer (Admin > Brands: a minimum order). Over it, delivery is free and the brand pays it. It uses the R150 fee for now; once Bob Go rates are live, take the actual courier price off the brand's payout instead. Manual payouts must deduct `deliveryCovered` too.
- **Collection (built):** Super Admin turns it on per brand (Admin > Brands > Collection, business addresses only). Not collected after 14 days: the team is emailed; cancelling and refunding is still done by hand. Once Bob Go booking is built, skip collected packages (`order.collectFrom`).

## Live data freshness, deleted products and renamed brands
- **Deleted products remain visible to customers (critical):** A product deleted in Admin still appeared on the public website and could be added to the cart, with the customer able to proceed toward checkout. Trace the full product lifecycle across Firebase/database reads, frontend state, browser storage, service workers/CDN/browser caches (if applicable), product detail pages, collection/homepage cards, cart and checkout. Identify the actual cause rather than applying a cosmetic workaround.
- **Deletion must take effect without a manual refresh:** When a product is deleted or unpublished, open customer sessions should stop displaying it promptly without requiring the customer to reload the page. Review stale in-memory product arrays, cached API responses, local/session storage and realtime update subscriptions. Use the existing architecture appropriately (realtime listeners or reliable cache invalidation/refetch); do not add indiscriminate polling or force full-page reloads as the fix.
- **Cart and checkout must reject deleted/unavailable items:** Remove or clearly flag stale cart lines when product data changes, and revalidate every product, variant, availability and price against authoritative server/database data when the cart is viewed and again when an order is submitted. A deleted/unpublished product must never be purchasable just because it remains in an old tab or saved cart. Block checkout for invalid items and explain what changed; never trust client-side cart data as the source of truth.
- **Website content updates must propagate across long-lived sessions:** Investigate the broader suspected stale-content issue. When Admin changes homepage hero images/sections or other site content, visitors who leave the same tab open for hours or days should receive current published content without needing a manual refresh. Establish a consistent freshness/invalidation strategy for product data, brand data and editable website content, including any API/CDN/browser caching and deployment/service-worker behaviour. Avoid unnecessarily disabling all caching if targeted invalidation or versioning can solve it.
- **Renamed brands still show the old name on the homepage:** After editing/renaming a brand or vendor in Admin, the homepage continues displaying its previous name. Trace where homepage brand cards/sections get their data and check for duplicated denormalized brand names, stale frontend state, cached responses or old local-storage data. Make all public brand displays resolve to the latest saved, published brand record and update existing sessions without a manual refresh. Ensure the change does not break brand pages, product-to-brand associations, vendor admin access or historical orders.
- **Regression tests required:** Test product create/edit/delete/unpublish and brand rename in one browser tab while a separate customer tab remains open; test an already-open product page, collection/homepage cards, an existing cart and checkout; test a stale cart after a deletion; and test content/hero changes without reloading. Verify the backend independently rejects deleted/unavailable products at order creation. Preserve existing UI and unrelated functionality, and report the root cause, files changed and tests performed.


## Chat widget security audit (JAI) — before launch
- **Firebase Realtime Database rules — highest priority:** inspect the *deployed* rules for `live_chat`, `chat_inbox` and `staff_uids`. Do not assume the browser code or hidden UI protects conversations. Enforce permissions in Firebase rules/server-side: a customer must only read and write their own conversation; changing a session ID must not expose or alter another customer's chat; customers must never be able to grant themselves staff/admin access or edit staff UID records. Verify how customer identity is bound to a session and how staff permissions are granted.
- **Test chat access controls:** use two separate customer accounts/sessions and attempt cross-reading, cross-writing, changing session IDs, editing inbox metadata, setting `needsHuman`/assignment/status fields, and modifying `staff_uids`. Confirm every unauthorised attempt is denied by Firebase, not merely hidden by the UI. Test admin and Super Admin access separately.
- **Cloudinary upload abuse:** review the public unsigned upload preset and restrict it to the required image formats, upload size and intended upload options/folder where supported. Treat the cloud name and unsigned preset as public, not secrets. Add abuse controls/monitoring and check that outsiders cannot use the preset to upload arbitrary content or run up storage/bandwidth costs.
- **Validate inputs on trusted boundaries:** the chat's 1,000-character limit, image MIME/8 MB checks and session/name/email validation in JavaScript are useful UX checks but can be bypassed. Revalidate message lengths, allowed fields, identifiers, image type/size and any metadata in Firebase rules and/or server endpoints wherever possible. Never trust role, customer ID, session ID or permissions supplied by the browser.
- **Admin authentication and authorisation:** confirm every admin inbox read/write and staff-only action is protected by Firebase rules or a trusted server-side check tied to authenticated staff UIDs/roles. Do not rely on client-side role checks, a hidden admin page, or editable browser state.
- **Abuse and cost limits:** add appropriate rate limits/throttling for message sends, image uploads and AI replies; guard against scripted spam, repeated uploads and AI-cost abuse. Make sure limits are enforced somewhere a customer cannot bypass by editing JavaScript or calling endpoints directly.
- **Audit public endpoints and secrets:** review the Render chat/AI and Cloudinary-config endpoints for authentication needs, strict input validation, safe error responses and rate limiting. Scan the public GitHub repo and deployment configuration for accidentally committed API keys, service-account credentials or other secrets; rotate any exposed secrets. Public client config/API keys are not automatically secrets, but must be constrained with the provider's security controls.
- **XSS and rendering regression tests:** preserve the use of `textContent` for user-authored text; do not insert customer messages/names into `innerHTML` unsafely. Test messages containing HTML/script-like strings and unusual Unicode; verify they display as text and never execute. Validate image URLs before rendering and keep links opened in a safe way.
- **Separate checkout/order security review:** independently verify server-side checkout and order creation. Recalculate product availability, prices, discounts, shipping and totals from trusted data; reject deleted/unpublished products and tampered client-submitted amounts. Chat security checks do not prove checkout is secure.
- **Evidence and sign-off:** inspect the actual deployed Firebase rules and Render configuration, document findings, fix confirmed weaknesses, and rerun the tests above after changes. Do not mark the widget secure until access-control and abuse tests pass. No evidence of a compromise has been established; this is a security review/remediation checklist, not a claim that the site has been hacked.
